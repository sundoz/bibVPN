# Безопасность: модель угроз, меры защиты, результаты аудита

Документ технический. Объяснение для неспециалистов: [GUIDE.md, раздел 12](GUIDE.md#12-безопасность-простыми-словами).

## Что защищаем

| Актив | Где | Последствия утечки |
|---|---|---|
| Приватные ключи Reality, short ID | `state/bibvpn.yml`, `build/nodes/*/config.json`, `/usr/local/etc/xray/config.json` на сервере | Сервер можно выявить активным зондированием и заблокировать |
| UUID пользователей | state, `build/clients/*`, ссылки у пользователей | Чужой человек пользуется сервером |
| Доступ к серверу (SSH) | SSH-ключ оператора | Полный контроль над сервером и трафиком пользователей |
| Приватность пользователей | трафик через сервер | Раскрытие посещаемых ресурсов |
| Сам сервер (IP) | — | Блокировка, бан хостинга за абьюз |
| Токены подписок | state, `/etc/bibvpn/monitor.json` и `/var/lib/bibvpn/subs/` на хабе, у пользователей | Чужой получает актуальные ссылки пользователя |
| Токен Telegram-бота | state, `monitor.json` на хабе | Спам от имени бота, чтение сообщений бота |

## Модель угроз

| Нарушитель | Возможности | Меры |
|---|---|---|
| **ТСПУ (пассивно)** | Видит весь трафик клиент↔сервер, классифицирует по сигнатурам и статистике | Reality: TLS 1.3 с отпечатком Chrome и SNI реального сайта, один порт 443 |
| **ТСПУ (активно)** | Подключается к серверу, повторяет перехваченные рукопожатия | Без аутентификации Reality проксирует на реальный `sni` (проверено тестом). Повтор перехваченного рукопожатия не даёт туннеля: у нарушителя нет эфемерного ключа клиента, и он не может завершить TLS |
| **Интернет-сканеры и боты** | Перебор SSH, сканирование портов | Только ключи в SSH, fail2ban, ufw default deny, открыты 22 и 443 |
| **Пользователь туннеля** (в будущем посторонний клиент) | Отправляет произвольные запросы через сервер | Блокировка приватных, link-local и metadata-сетей, собственного IP сервера, loopback-сервисов (API Xray), SMTP, BitTorrent |
| **Уязвимость в Xray** | Выполнение кода в процессе Xray | Отдельный пользователь, только `CAP_NET_BIND_SERVICE`, песочница systemd (read-only FS, seccomp, W^X, без namespaces и т.д.) |
| **Подмена бинарника при скачивании** | MITM на пути к GitHub | Версия закреплена, sha256 сверяется |
| **Испорченный или подменённый state** | Правка YAML, вредоносный файл | `safe_load`, строгая валидация каждого поля при чтении и записи |
| **Изъятие хаба в РФ** (хостинг по требованию властей) | Доступ к `monitor.json`: ссылки всех пользователей (адреса серверов, UUID) | Принятый риск (ниже). Нет state, приватных ключей Reality и SSH-ключей к серверам. Ротация: `--rotate-keys`, `rotate-sub`. Альтернатива: хаб за границей |
| **Перехват подписки** | Подмена DNS, MITM | HTTPS с сертификатом Let's Encrypt. Свой домен вместо sslip.io |
| **Перебор токенов подписки** | Запросы `/s/<guess>` | 192 бита случайности, всё кроме `/s/<token>` отдаёт 404, листинга каталога нет |
| **Кража ноутбука оператора** | Доступ к state и SSH-ключу | Права 0600/0700, passphrase на ключ (рекомендация), `--rotate-keys` |

## Аудит (2026-09-26)

Методы: ручной разбор кода и плейбуков, bandit, pip-audit,
`systemd-analyze security`, проверки на развёрнутом тестовом сервере (Ubuntu 24.04
с systemd в Docker): попытки достучаться до служб сервера через туннель, проверка
итоговой конфигурации sshd, мутационная проверка тестов (намеренные поломки кода
должны ронять тесты).

### Найдено и исправлено

| # | Серьёзность | Проблема | Исправление | Проверка |
|---|---|---|---|---|
| 1 | **Высокая** | Вход по паролю в SSH оставался включён на облачных образах. sshd берёт **первое** значение опции, а `50-cloud-init.conf` (`PasswordAuthentication yes`) читался раньше нашего `90-bibvpn.conf`. Плейбук при этом сообщал об успехе | Файл переименован в `00-bibvpn.conf`, старый удаляется, после применения плейбук проверяет итоговую конфигурацию через `sshd -T` | Воспроизведено на тестовом сервере. Интеграционный тест подкладывает `50-cloud-init.conf` и проверяет `sshd -T` |
| 2 | Средняя | Нет валидации входных данных: `host`, `sni`, `ssh_user` попадали в инвентарь Ansible, где `{{ ... }}` исполняется как шаблон на машине оператора (`lookup('pipe', ...)`), в YAML и в SSH-опции | Строгие белые списки для всех полей при `save` и `load`, проверка соответствия публичного и приватного ключа, нормализация регистра | `tests/test_security.py`: инъекции, подменённые state-файлы, YAML-теги |
| 3 | Средняя | Если оператор пропустит правило, пользователь туннеля может достучаться до служб на **собственном публичном IP** сервера: такое соединение идёт через loopback, мимо ufw. Защита от приватных сетей зависела только от содержимого `geoip.dat` | Явный список приватных, link-local, CGNAT, multicast и metadata-сетей плюс IP самой ноды. У Xray 26 есть собственная встроенная блокировка приватных адресов во `freedom`, получилось два уровня защиты | Интеграционный тест пытается через туннель получить SSH-баннер сервера (`127.0.0.1`, `localhost`, `::1`, IP ноды) и достучаться до API Xray. При ручной проверке с отладочным журналом все попытки уходили в `block` |
| 4 | Средняя | Нет блокировки исходящей почты: сервер можно использовать для спама, и хостинг забанит его | Блокировка портов 25, 465, 587 | Юнит-тест |
| 5 | Низкая | Каталоги `state/` и `build/` создавались с правами 0755 (файлы уже были 0600) | 0700 | Юнит-тест |
| 6 | Низкая | Песочница systemd была базовой, была лишняя `CAP_NET_ADMIN` | Добавлены `SystemCallFilter`, `MemoryDenyWriteExecute`, `RestrictNamespaces`, `ProtectProc` и др. Оценка `systemd-analyze security` 1.6 | Интеграционный тест требует оценку < 3.0 |
| 7 | Средняя (надёжность) | `ufw limit` на SSH отвергал серию подключений Ansible, и деплой терял доступ к серверу | `allow`, перебор отсекает fail2ban | Найдено интеграционным тестом |

### Аудит хаба (подписки и мониторинг)

| # | Серьёзность | Проблема | Исправление | Проверка |
|---|---|---|---|---|
| 8 | Средняя (надёжность) | Проверки не переходили по HTTP-редиректам: любой тестовый URL за CDN или с редиректом давал ложное «загрузка замирает» | `-L --max-redirs 3` | Найдено интеграционным тестом, юнит-тест на флаг |
| 9 | Средняя | Файлы состояния, созданные до появления подписок, получали новый токен при каждом запуске: ссылки подписок «плавали» | Одноразовая миграция при загрузке, новые поля сразу сохраняются | Юнит-тест |

Свойства, проверенные тестами:
- все значения, которые попадают в Caddyfile, JSON и заголовки (домен, название,
  URL, токен и chat id Telegram), проходят строгую валидацию: инъекции в
  Caddyfile и заголовки отвергаются;
- Caddy без журнала доступа, токены не оседают на диске. Неизвестный токен, `/`
  и `/s/` дают 404;
- отключённый пользователь пропадает из подписок (его файл удаляется), см.
  интеграционный тест;
- мониторинг работает от отдельного пользователя в песочнице systemd
  (оценка 1.4), тестовый Xray-клиент тоже (1.4). Прокси-переменные окружения
  игнорируются, проверки не уходят мимо туннеля;
- токен Telegram передаётся curl через stdin, а не в аргументах (не виден в `ps`);
- проверки идут от отдельной служебной учётки `_monitor`, которая есть на серверах,
  только если настроен хаб.

### Внешнее ревью (2026-09-27)

| # | Серьёзность | Проблема | Исправление | Проверка |
|---|---|---|---|---|
| 10 | **Высокая** | `deploy --check` добавляет `--diff`: при изменении конфига Ansible выводил в терминал (и в CI-логи) приватный ключ Reality и UUID пользователей. Проверка конфига передавала его содержимое аргументом задачи (stdin), что видно в `-v` и сообщениях об ошибках | Файлы с секретами (`config.json`, `probe-xray.json`, `monitor.json`) копируются с `diff: false`. Проверка идёт по пути к промежуточному файлу (`*.staged.json`), содержимое в аргументы не попадает | Статический тест по всем задачам ролей; интеграционный тест ищет ключи, UUID и токены в выводе `--check` на чистых и на изменённых серверах |
| 11 | **Высокая** | `node set --disable` убирал сервер из инвентаря, и уже работающий Xray продолжал принимать старые ссылки. Оператор мог считать доступ отозванным | Отключённые серверы остаются в инвентаре: `deploy` останавливает Xray, удаляет конфиг с ключами, закрывает порт. `node rm` отказывается удалять работающий сервер. `deploy` больше не отказывается работать, когда отключены все серверы (ошибка найдена интеграционным тестом) | Интеграционный тест: после отключения Xray остановлен и выключен, конфига нет, порт закрыт, старая ссылка не работает |
| 12 | Средняя | IPv6-адрес сервера принимался, но Xray слушал только `0.0.0.0` | Публичный вход слушает `::` (dual-stack). Go сам выставляет `IPV6_V6ONLY=0`, а при выключенном в ядре IPv6 откатывается на IPv4 (проверено в среде без IPv6) | Юнит-тесты, проверка конфига Xray. Живое подключение по IPv6 не проверялось: в тестовой среде нет IPv6 |
| 13 | Средняя | `deploy --check` падал на чистом сервере: нет бинарника, каталогов, пользователей, `python3-apt` | Задачи, которые зависят от созданного в том же запуске, в check mode пропускаются. На ни разу не развёрнутом сервере предпросмотр ограничен базовой подготовкой, с сообщением. Без `python3-apt` предпросмотр пакетов пропускается с предупреждением | Интеграционный тест: `deploy --check` на чистых сервере и хабе; статический тест на условия check mode |

### Проверено, проблем нет
- **bandit**: только низкая серьёзность и ожидаемые срабатывания: `subprocess` со
  списком аргументов без shell, `curl` по имени (PATH задаёт systemd), пустая строка
  как «пароль» (проверка ненастроенного токена). В CI bandit запускается с порогом
  «средняя и выше».
- **pip-audit**: уязвимости только в pip и setuptools окружения разработчика, не в
  зависимостях проекта.
- Секретов в инвентаре нет (его читает Ansible, он может попасть в логи).
- API Xray (Stats и Handler) слушает только `127.0.0.1` и через туннель недоступен.
- Reality: `show: false`, short ID полной длины (16 hex), журнал посещений выключен.
- Отключённый пользователь теряет доступ после `deploy` (интеграционный тест).
- Повторный `deploy` ничего не меняет (интеграционный тест). Ручные правки на
  сервере не «разъезжаются» с состоянием.

## Остаточные риски и рекомендации

| Риск | Статус |
|---|---|
| Абстрактный unix-сокет XHTTP (`@bibvpn-xhttp`) доступен любому локальному процессу сервера. Требует UUID, на однопользовательском сервере не проблема | Принят |
| API Xray на `127.0.0.1:10085` без аутентификации: любой локальный процесс может добавлять пользователей. На сервере нет других пользователей | Принят; для коммерции перевести на unix-сокет с правами |
| Для ноды, заданной именем (не IP), её собственный адрес не блокируется на уровне Xray (остаётся встроенная защита Xray для приватных адресов) | Рекомендация: указывать IP |
| Нет автоматического бэкапа state | Этап 2 (age/sops) |
| Доверие к первому SSH-подключению (TOFU) | Рекомендация: сверить отпечаток ключа сервера с панелью хостинга |
| Юридические риски при коммерческом использовании в РФ | Нужна консультация юриста до запуска |
| **Хаб в РФ хранит ссылки всех пользователей.** При изъятии раскрываются адреса серверов и доступ к ним (не личные данные и не история) | Принят для личного использования; для коммерции рассмотреть хаб только с подписками без мониторинга или шифрование ссылок на клиенте |
| sslip.io: чужой DNS. Его владелец теоретически может выпустить сертификат на наше имя и подменить подписку | Для коммерции только свой домен (+ CAA-запись) |
| **Hysteria2: самоподписанный сертификат.** Подлинность сервера держится на отпечатке `pinSHA256` в ссылке. В ссылке стоит `insecure=1`, чтобы клиенты не искали центр сертификации. Клиент, который не поддерживает `pinSHA256`, подключится без проверки, и при активной подмене сервера UUID пользователя утечёт | Принят. Клиенты на ядре Xray и официальный Hysteria проверяют pin, хаб проверяет его всегда (`pinnedPeerCertSha256`, тест с неверным pin отклоняется). Альтернатива: настоящий сертификат на домен ноды |
| Hysteria2 открывает UDP 443: ещё один публичный вход | Та же авторизация по UUID, запросы без пароля проксируются на `sni` (masquerade), отключается `node set --no-hy2`, у отключённой ноды порт закрывается (интеграционный тест) |
| SOCKS-порты тестового клиента на хабе (`127.0.0.1:21000+`) без аутентификации: любой локальный процесс хаба может ходить через туннели | Принят: на хабе нет других пользователей |
| Caddy admin API на `localhost:2019` | Штатное поведение Caddy, доступен только локально |
| Хостинг видит, к каким ресурсам обращается сервер | Принципиальное ограничение: это средство обхода блокировок, а не анонимности |

## Как перепроверить

```bash
make test          # 168 тестов: валидация, инъекции, права файлов, правила маршрутизации
make integration   # на тестовых сервере и хабе: sshd -T, открытые порты, fail2ban,
                   # песочницы, недоступность служб сервера через туннель,
                   # подписки по HTTPS, сценарий «сервер упал / поднялся»
.venv/bin/pip install bandit pip-audit && .venv/bin/bandit -r bibvpn && .venv/bin/pip-audit
```
