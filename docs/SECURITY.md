# Безопасность: модель угроз, меры защиты, результаты аудита

Документ технический. Объяснение для неспециалистов: [GUIDE.md, раздел 11](GUIDE.md#11-безопасность-простыми-словами).

## Что защищаем

| Актив | Где | Последствия утечки |
|---|---|---|
| Приватные ключи Reality, short ID | `state/bibvpn.yml`, `build/nodes/*/config.json`, `/usr/local/etc/xray/config.json` на сервере | Сервер можно выявить активным зондированием и заблокировать |
| UUID пользователей | state, `build/clients/*`, ссылки у пользователей | Чужой человек пользуется сервером |
| Доступ к серверу (SSH) | SSH-ключ оператора | Полный контроль над сервером и трафиком пользователей |
| Приватность пользователей | трафик через сервер | Раскрытие посещаемых ресурсов |
| Сам сервер (IP) | — | Блокировка, бан хостинга за абьюз |

## Модель угроз

| Нарушитель | Возможности | Меры |
|---|---|---|
| **ТСПУ (пассивно)** | Видит весь трафик клиент↔сервер, классифицирует по сигнатурам и статистике | Reality: TLS 1.3 с отпечатком Chrome и SNI реального сайта, один порт 443 |
| **ТСПУ (активно)** | Подключается к серверу, повторяет перехваченные рукопожатия | Без аутентификации Reality проксирует на реальный `sni` (проверено тестом). Повтор перехваченного рукопожатия не даёт туннеля: у нарушителя нет эфемерного ключа клиента, и он не может завершить TLS |
| **Интернет-сканеры и боты** | Перебор SSH, сканирование портов | Только ключи в SSH, fail2ban, ufw default deny, открыты 22 и 443 |
| **Пользователь туннеля** (в будущем посторонний клиент) | Отправляет произвольные запросы через сервер | Блокировка приватных, link-local и metadata-сетей, собственного IP сервера, loopback-сервисов (API Xray), SMTP, BitTorrent |
| **Уязвимость в Xray** | Выполнение кода в процессе Xray | Отдельный пользователь, только `CAP_NET_BIND_SERVICE`, песочница systemd (read-only FS, seccomp, W^X, без namespaces и т.д.) |
| **Подмена бинарника при скачивании** | MITM на пути к GitHub | Версия закреплена, sha256 сверяется |
| **Испорченный или подменённый state** | Правка YAML, вредоносный файл | `safe_load`, строгая валидация каждого поля при чтении и записи |
| **Кража ноутбука оператора** | Доступ к state и SSH-ключу | Права 0600/0700, passphrase на ключ (рекомендация), `--rotate-keys` |

## Аудит (2026-09-26)

Методы: ручной разбор кода и плейбуков, bandit, pip-audit,
`systemd-analyze security`, проверки на развёрнутом тестовом сервере (Ubuntu 24.04
с systemd в Docker): попытки достучаться до служб сервера через туннель, проверка
итоговой конфигурации sshd, мутационная проверка тестов (намеренные поломки кода
должны ронять тесты).

### Найдено и исправлено

| # | Серьёзность | Проблема | Исправление | Проверка |
|---|---|---|---|---|
| 1 | **Высокая** | Вход по паролю в SSH оставался включён на облачных образах. sshd берёт **первое** значение опции, а `50-cloud-init.conf` (`PasswordAuthentication yes`) читался раньше нашего `90-bibvpn.conf`. Плейбук при этом сообщал об успехе | Файл переименован в `00-bibvpn.conf`, старый удаляется, после применения плейбук проверяет итоговую конфигурацию через `sshd -T` | Воспроизведено на тестовом сервере. Интеграционный тест подкладывает `50-cloud-init.conf` и проверяет `sshd -T` |
| 2 | Средняя | Нет валидации входных данных: `host`, `sni`, `ssh_user` попадали в инвентарь Ansible, где `{{ ... }}` исполняется как шаблон на машине оператора (`lookup('pipe', ...)`), в YAML и в SSH-опции | Строгие белые списки для всех полей при `save` и `load`, проверка соответствия публичного и приватного ключа, нормализация регистра | `tests/test_security.py`: инъекции, подменённые state-файлы, YAML-теги |
| 3 | Средняя | Если оператор пропустит правило, пользователь туннеля может достучаться до служб на **собственном публичном IP** сервера: такое соединение идёт через loopback, мимо ufw. Защита от приватных сетей зависела только от содержимого `geoip.dat` | Явный список приватных, link-local, CGNAT, multicast и metadata-сетей плюс IP самой ноды. У Xray 26 есть собственная встроенная блокировка приватных адресов во `freedom`, получилось два уровня защиты | Интеграционный тест пытается через туннель получить SSH-баннер сервера (`127.0.0.1`, `localhost`, `::1`, IP ноды) и достучаться до API Xray. При ручной проверке с отладочным журналом все попытки уходили в `block` |
| 4 | Средняя | Нет блокировки исходящей почты: сервер можно использовать для спама, и хостинг забанит его | Блокировка портов 25, 465, 587 | Юнит-тест |
| 5 | Низкая | Каталоги `state/` и `build/` создавались с правами 0755 (файлы уже были 0600) | 0700 | Юнит-тест |
| 6 | Низкая | Песочница systemd была базовой, была лишняя `CAP_NET_ADMIN` | Добавлены `SystemCallFilter`, `MemoryDenyWriteExecute`, `RestrictNamespaces`, `ProtectProc` и др. Оценка `systemd-analyze security` 1.6 | Интеграционный тест требует оценку < 3.0 |
| 7 | Средняя (надёжность) | `ufw limit` на SSH отвергал серию подключений Ansible, и деплой терял доступ к серверу | `allow`, перебор отсекает fail2ban | Найдено интеграционным тестом |

### Проверено, проблем нет
- **bandit**: только ожидаемые срабатывания: `subprocess` со списком аргументов без
  shell; `0.0.0.0` для публичного входа Xray (он так и задуман).
- **pip-audit**: уязвимости только в pip и setuptools окружения разработчика, не в
  зависимостях проекта.
- Секретов в инвентаре нет (его читает Ansible, он может попасть в логи).
- API Xray (Stats и Handler) слушает только `127.0.0.1` и через туннель недоступен.
- Reality: `show: false`, short ID полной длины (16 hex), журнал посещений выключен.
- Отключённый пользователь теряет доступ после `deploy` (интеграционный тест).
- Повторный `deploy` ничего не меняет (интеграционный тест). Ручные правки на
  сервере не «разъезжаются» с состоянием.

## Остаточные риски и рекомендации

| Риск | Статус |
|---|---|
| Абстрактный unix-сокет XHTTP (`@bibvpn-xhttp`) доступен любому локальному процессу сервера. Требует UUID, на однопользовательском сервере не проблема | Принят |
| API Xray на `127.0.0.1:10085` без аутентификации: любой локальный процесс может добавлять пользователей. На сервере нет других пользователей | Принят; для коммерции перевести на unix-сокет с правами |
| Для ноды, заданной именем (не IP), её собственный адрес не блокируется на уровне Xray (остаётся встроенная защита Xray для приватных адресов) | Рекомендация: указывать IP |
| Нет автоматического бэкапа state | Этап 2 (age/sops) |
| Доверие к первому SSH-подключению (TOFU) | Рекомендация: сверить отпечаток ключа сервера с панелью хостинга |
| Юридические риски при коммерческом использовании в РФ | Нужна консультация юриста до запуска |
| Хостинг видит, к каким ресурсам обращается сервер | Принципиальное ограничение: это средство обхода блокировок, а не анонимности |

## Как перепроверить

```bash
make test          # 87 тестов: валидация, инъекции, права файлов, правила маршрутизации
make integration   # на тестовом сервере: sshd -T, открытые порты, fail2ban,
                   # песочница, недоступность служб сервера через туннель
.venv/bin/pip install bandit pip-audit && .venv/bin/bandit -r bibvpn && .venv/bin/pip-audit
```
